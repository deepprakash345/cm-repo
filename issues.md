# Custom AEM Forms Component Issues to Check

- **Build with a supported JDK.** Verify `mvn -version`; Maven can use a different Java version than expected. Use the project's configured Java version rather than relying on shell defaults.
- **Export Java model APIs used by HTL.** Sling Model registration does not make a Java package visible to HTL's compiler. With this project's version-based bnd export configuration, add a versioned `package-info.java` and verify the bundle's `Export-Package` header. Missing exports caused `StarRating cannot be resolved to a type`.
- **Rebuild the actual deployment artifact after changes.** A fresh core JAR does not update an existing `all/target` ZIP. Inspect the embedded bundle, not just the standalone JAR, before deployment.
- **Keep HTL comparisons numeric and null-safe.** Optional defaults may be null or empty. Normalize valid authored values and use a numeric rendering helper for comparisons; preserve an unset form value as null and exclude rendering-only helpers from JSON. Comparing an unset rating with a star number caused the HTL operand-type error.
- **Load the final Forms runtime before registering custom fields.** Loading `runtime.base`, registering a custom field, and then loading `runtime.all` can replace the runtime and lose the field registry. The client library dependency was changed to `core.forms.components.runtime.all`, but the live interaction issue remained unresolved after deployment.
- **Verify interaction, not just rendering or deployment completion.** A successful build, completed RDE update, HTTP 200, and visible controls do not prove model binding works. Test real mouse selection, filled-star updates, numeric model values, clearing, and keyboard interaction on the deployed page in runtime mode (`wcmmode=disabled`). Isolated interaction tests passed, but the deployed selection test still failed; further initialization tracing was interrupted.
